在这篇 Blog 里我希望聊一聊我是如何理解以及如何完成一个 RAG 的系统并且考虑对其进行优化的。

这篇文章中的问题也可以和[Embedding Atlas：用可视化理解 RAG 的嵌入空间](/blog/2026/05/29/embedding-atlas-rag-embedding-visualization/)放在一起阅读，以比较相近的概念如何在不同语境中展开。

我在刚开始研究 AI Agent 的时候，对 RAG 这项技术就不是很热衷；进行少样本的提示最初是有价值的，但当知识库更大，人类意图对其更充分的模型得到训练以后，这些提示就可能会从提示模型解决问题的方向变成约束其自我发挥的能力。构建一个 AI Agent 需要在约束和自由之间取得平衡，我一直认为 RAG 是一项妥协的技术，我们应当关注的是构建解决任务的系统本身，而 RAG 只是其中的一个组件。

不过最近想法有一些变化，我在 7 月重新盘点过去半年的 AI Agent 技术发展的时候想到了它。或许 RAG 确实有未来，训练可以得到知识和意图对齐，但得不到现实世界繁杂的习惯。在这个时候，去收集和清洗数据，去思考知识应该如何存储与迭代，我们可能暂时只是在做一个 QA Bot，但我们的目标是构建一个一个系统化的知识系统，让 AI 能够理解繁杂的现实世界与真实工程。或许这才是现在研究 RAG 的意义。

这篇 Blog 更多的会从一些实践出发，聊聊我在不同的问题上如何构建一个 RAG 系统；如何分离事实层，增强层，查询层；如何理解 Agentic RAG 和最基本的信息查询与聚合；如何在市面上数量繁多，成本各异的 RAG 方法中寻找适合的解决方案。我们会从各个问题本身来带出技术，而不是给读者一个看似有用的巨大对比表格。

和我做的很多 Agent 项目一样，我希望能够去更多的回答为什么。Agent 的终局并不复杂，但为什么选择这个技术，为什么选择迭代，这个过程才是做 AI Agent 以及 RAG 系统的时候更值得回答的问题。

LlamaIndex 其实是个不错的去做 RAG 的项目，但是在一个 AI Coding 的时代去学习过多的封装结构并不让人舒服，从各个系统底层开始拼装可以去更好的做一个工程可用的系统，也不需要引入很多历史遗留无用的模块。

## POPO QA Bot

POPO QA Bot 是我还在网易的时候去做的一个问题，整体算是一个很简单的问题，但越是简单的问题越适合拿来开场，我们可以聊的细一点。

我们的数据源来自 POPO 的文档库，你可以把它理解为网易内部的飞书文档。在整个项目长期的开发中，我们逐渐形成了一个基于文件系统的文档数据库。根据策划、程序等等游戏开发中的分类，基本上划分了十几个大类，部分大类中会嵌套一些2级或者3级的小类，有些类别内容比较少，那么就只有大类。数据源质量一般，包括 `.pptx`  `.docx`   `.pdf`   `.md`   `.xlsx`  `.html` 多种格式，最终的目标是构建一个能够基于文档库回答问题，并且最好能够继续进化的 QA 机器人。

其实聊到这里，我们最终的问题就已经比较明确了，我们需要一个手段去能够相对统一地处理这种混合来源的数据，并且结合我们对这些数据本身的理解进行适当的定制处理方式。然后我们需要构建一个简单的检索层，去回答问题，最后思考这个系统应该如何进一步的进化。

我们来逐个展开。

### 构建事实层

这是第一个 RAG 项目，所以说我需要聊一聊我个人最基本的一个倾向。

我不喜欢把所有的文档全部转化为标准的 markdown，然后设置一个切片大小，最后再搞一些 overlap。这个思路非常容易实现，也可以很好地聚合各种来源的数据。但是它损失了文档本身的结构，人类不会去阅读一个没有结构的文档，那么我们为什么一定要让 AI 去阅读一个没有结构的文档？DeepRead 是我很喜欢的 Paper, PageIndex 也是对于构建知识库不得不聊的开源项目，让我们在这一步保留结构，而不是去破坏它。

既然我们需要保留文档结构，Docling 就很适合放在事实层这一层。它是 IBM 发起的开源文档解析框架，支持多种 Office、PDF、HTML、Markdown 等格式，并提供统一的 `DoclingDocument` 表示。它还带有 OCR、版面分析和图片理解相关能力。对大多数内部文档来说，这已经足够了；如果遇到版式特别复杂的 PDF，我会考虑 MinerU，具体可以参考[《让 OCR 再次伟大》](/blog/2026/07/04/make-ocr-great-again/)。

这个项目里的六种输入格式是 `.pptx`、`.docx`、`.pdf`、`.md`、`.xlsx` 和 `.html`。它们最后被归一化为三类结构：文档树、PPT 和表格。三类结构都进入 `DoclingDocument`，但不要求使用完全相同的转换方式。我们会在后面进行展开。

#### DoclingDocument 的基本形式

`DoclingDocument` 不是一段被重新排版的 Markdown，而是一个带有结构和溯源信息的文档对象。它通常包含文档名称、来源、版本、页面信息，以及下面这些内容集合：

- `body`：正文的根节点，保存文档的阅读顺序和层级关系；
- `groups`：章节、列表等容器节点，也可以在我们的适配逻辑中表示一张幻灯片或一个 Sheet；
- `texts`：标题、段落、列表项、代码和公式等文本节点；
- `tables`：表格节点，内部还可以继续保存单元格网格；
- `pictures`：图片节点，可以带有图片位置、图注和原始页面信息。

`body` 和各个节点并不一定把所有内容直接嵌套在一起。树中的 `children` 通常保存 JSON Pointer，例如 `#/texts/0`；被引用的节点再通过 `parent` 指回自己的容器，`self_ref` 则是它自己的稳定地址。对于 PDF 或 PPTX，节点还可以通过 `prov` 保存页码和 `bbox`，这样检索结果最后能够回到原始页面，而不是只剩下一段无法定位的文本。

值得注意的一点是，对于一个 DoclingDocument，核心内容以及body树的结构实际上是分离的，内容会被统一放在列表中，最后我们在树中只会进行引用。这样的话可以避免在树中同时存储结构和正文带来的过大阅读负担。最小化地看，一个文档大概是下面这样的结构。

```text
DoclingDocument
│
├── body: GroupItem
│   └── children
│       ├── Ref("#/texts/0")
│       ├── Ref("#/groups/0")
│       └── Ref("#/tables/0")
│
├── groups[]
│   └── GroupItem(...)
│
├── texts[]
│   ├── TitleItem(...)
│   ├── SectionHeaderItem(...)
│   └── TextItem(...)
│
├── tables[]
│   └── TableItem(...)
│
├── pictures[]
│   └── PictureItem(...)
│
├── key_value_items[]
├── form_items[]
├── field_regions[]
├── field_items[]
│
└── pages{}
```

```json
{
  "schema_name": "DoclingDocument",
  "version": "1.0.0",
  "name": "example.docx",
  "origin": {
    "filename": "example.docx",
    "mimetype": "application/vnd.openxmlformats-officedocument.wordprocessingml.document"
  },
  "body": {
    "self_ref": "#/body",
    "children": [
      { "$ref": "#/texts/0" },
      { "$ref": "#/groups/0" }
    ]
  },
  "groups": [
    {
      "self_ref": "#/groups/0",
      "label": "section",
      "name": "第一章",
      "parent": { "$ref": "#/body" },
      "children": [
        { "$ref": "#/texts/1" },
        { "$ref": "#/tables/0" }
      ]
    }
  ],
  "texts": [
    {
      "self_ref": "#/texts/0",
      "label": "title",
      "text": "文档标题",
      "parent": { "$ref": "#/body" }
    },
    {
      "self_ref": "#/texts/1",
      "label": "paragraph",
      "text": "第一章中的一段正文",
      "parent": { "$ref": "#/groups/0" }
    }
  ],
  "tables": [
    {
      "self_ref": "#/tables/0",
      "label": "table",
      "parent": { "$ref": "#/groups/0" },
      "data": { "table_cells": [] }
    }
  ],
  "pictures": []
}
```

在标准 Docling 流程中，解析器负责把源文件转换成这个对象，之后可以继续导出为 Markdown、HTML 或 JSON。先恢复文档对象，再在它上面做切分、摘要和检索。直接把所有输入压成一段 Markdown，相当于先丢掉结构，再让后面的系统猜结构在哪里。

#### 文档树：DOCX、PDF、Markdown 和 HTML

这四类格式本身都存在一定的文档层级。标题下面可以有段落、列表、表格和图片，章节之间还存在父子关系。因此我们优先使用 Docling 的标准解析流程，保留它恢复出来的文档树：

```text
DoclingDocument
└── body
    ├── text(label="section_header")
    ├── group(label="section")
    │   ├── text(label="paragraph")
    │   ├── group(label="list")
    │   ├── table
    │   └── picture
    └── group(label="section")
        └── text(label="paragraph")
```

PDF 通常还能提供页码和坐标，DOCX、HTML 和 Markdown 则更接近连续的流式文档。定位信息不必强行统一：有页面坐标时就保存 `page_no` 和 `bbox`，没有时至少保留章节路径、节点引用和原始文件信息。

#### PPT：PPTX 按幻灯片分组

PPTX 中的文本、图片和表格通常是按页面摆放的元素，页面之间未必存在像 DOCX 那样可靠的章节层级。这个项目采用一个确定的归一化方式：每一张幻灯片对应一个 `group`。

```text
DoclingDocument
└── body
    ├── group(label="slide", name="slide-0")
    │   ├── text
    │   ├── picture
    │   └── table
    ├── group(label="slide", name="slide-1")
    │   └── picture
    └── group(label="slide", name="slide-2")
        ├── text
        └── table
```

这只是项目侧的组织策略，不代表所有 PPTX 都天然拥有这样的章节结构。幻灯片标题、页面编号、元素坐标和源文件信息都作为事实保存。有些 PPTX 是存在一些章节目录关系的，那么我们可以去利用，但是我所遇到的基本都没有，处理方式要随着数据本身的变化而变化，我们后面还会遇到这个问题。

#### 表格：XLSX 按 Sheet 分组

XLSX 的主要信息通常在工作表和单元格里。对于内部排班表、排期表和字段表，我们让一个 Sheet 对应一个 `group`，在组内保存一个或多个 `table`：

```text
DoclingDocument
└── body
    ├── group(label="sheet", name="目录")
    │   └── table
    ├── group(label="sheet", name="排班表")
    │   └── table
    └── group(label="sheet", name="字段说明")
        └── table
```

表格节点内部可以继续展开为 `tables[].data.table_cells[]`。单元格至少需要保留文本、行列位置、合并范围以及是否为行表头或列表头等信息：

```json
{
  "row_span": 1,
  "col_span": 1,
  "start_row_offset_idx": 4,
  "end_row_offset_idx": 5,
  "start_col_offset_idx": 2,
  "end_col_offset_idx": 3,
  "text": "夜班",
  "column_header": false,
  "row_header": false,
  "row_section": false
}
```

#### 事实层的边界

经过上述处理，所有输入最终都有一个统一的结构化落点，但这个落点只负责记录源文件中实际存在的内容。DoclingDocument 是唯一的结构化事实层；各格式解析器负责忠实映射，不能在这里加入模型猜测。

切分、图片描述、表格摘要、Embedding、Rerank、Agent 和生成回答都属于事实层之上的派生过程。它们可以通过节点引用回到原文，也可以在查询时扩展上下文，但不能反向修改事实层。这样做有一个实际好处：换 Embedding 模型时不需要重新解析原始文件，修改图片摘要提示词时也不会改变文档本身。

我们需要降低整个系统的耦合程度。这就是为什么事实层会和后面的系统分离。

### 增强层与被检索的资料

对原始数据进行增强，是做 RAG 完全不可能避免掉的东西。我们会在这里一并考虑如何处理事实层，去进行一些增强，并且得到最后的被检索资料，需要注意的是，增强与检索层本身是一个完全独立的层级，我们不会去修改事实层，而是形成单独的数据库，避免事实以及模型增强后的幻觉混为一谈。

最基本的增强关于图与表。我们不会搞一个多模态的嵌入器，也不可能直接去将表格的所有内容变成一个嵌入向量。因此图和表都需要被总结，变成一段文本，然后再被检索，最终回到事实。这是最基本的需要做的内容。

如果我们希望构建一个类似于 DeepRead 或者 PageIndex的结构化索引系统，那么针对每一个自然结构进行一定的 Summary，也是查询的时候所必需的。

这里我只聊聊我是怎么做的，作为一个参考。

实际上，增强层和检索层在这个项目中是被一并构建的。对于向量以及 BM25 的检索方式，我们需要构建 Chunk 作为检索层，因此这里我所作的只是稍微调整了一下 Docling 的 HybridChunker 的逻辑。

我在大部分地方依旧复用 HybridChunker 保持 HybridChunker 的完整上下文感知逻辑： 它会先默认将每一个最小节点作为一个 Chunk，然后考虑同一层级上的合并，直到接近我们所设置的目标 Chunk 的大小；对于那些单个 Node 就已经超过了设置大小的，则有一些句子感知的切分（无 Overlap）。生成的 Chunk 的 `meta.doc_items` 依然会包含指向原文档 TableItem 或 PictureItem 的指针。任何合并都不会跨 Chapter 保护章节逻辑。

我这里为了更好的处理项目图片和表格，设置了一些单独的逻辑。图片在默认行为下是没有什么增强的，它会直接和 caption 放在一起，我在 Chunker 中增加了 VLM 对图片的理解，并在 Chunker 将其与 Captain 合并作为被检索文字。HybridChunker 的默认表格处理会在表格较大时将表格进行切分，并且重复表头，我完全放弃了这个逻辑，因为项目中的大部分表格更多的是排班表和工期表，不太好切分，所以最终只会生成一个表格的 summary 作为被检索文本。无信息的图片不会被分析，如 LOGO 装饰图片等，一个单独的请求用来过滤。

关于 chunk_size (token 计)
* 知识库 QA： 一般 50-200，取决于问题和答案的长度
* 一般技术文档：400 左右，正负 200
* 论文、长报告、长文件：600 左右，正负 200
一般需要实验辅助确认，仅作为经验参考；本项目在试验后选择了 400，基于 50 个测试样例给出。

Chunker 之后是面向 Chunk 可能被查询到的总结，也是增强与检索层的第二步。这是针对 Chunk 层级的，表格和图片不考虑二次总结直接复用。每个 Chunk 会让 AI 进行一个简单的 Summary。提前做重度预处理，通过在构建期（Build-time）消耗算力去提纯知识，从而换取检索期（Run-time）极高的召回率和信噪比。

至于他们要如何进入查询库，包含三种思路
* 只检索 Summary
* Summary 和 Content 层拼接
* Summary 和 Content 层独立
我们使用了第二种，但是在实际的项目测试中，没有在这方面发现区别。

Chunk 已经逐渐的离开的事实层，变成了增强后资料层的一部分。每个 Chunk 最终会包含切片后的文本，一些元数据索引以及对于 DoclingDocument 事实层的索引。

注意：我们使用 contextualize(chunk) 自动拼接标题结构到每个 Chunk 中，方便做Dense和BM25检索；这个行为是我的个人偏好，未经可靠的实验验证。

对于结构化索引的 Agentic RAG 系统，我们直接复用了 PageIndex, 没有在这方面投入过多的优化精力。构建了一个简单的文档索引系统，通过一些 Summary 和文件夹名称方便 Agent 去找到对应文档，文档内检索则完全是复用了 PageIndex 的系统，预先构建索引树和 Summary 实现查询。

虽然我很喜欢 Deepread 和 PageIndex 的结构化索引查询思路，但其消耗的 token 过于巨大且耗时较长，带来的收益却微乎其微，因此在默认的系统中结构化索引查询其实被关闭了。

### 查询层与查询的实现

和我的个人习惯一样，我们在这个项目的查询数据库主要使用了SQLite，对于这个系统目前的数据规模，它已经足够。向量数据库和文本数据库相互独立；对于向量数据，每个 Chunk 使用智谱的 Embedding3-2048 进行向量化，在查询的时候也是同样的检索方式，使用 SQLite-vev 进行向量召回；对于文本数据库，则直接存入，查询时使用 FTS5 召回。

对于每个查询的重写是任何查询层都需要考虑的问题。在这个系统中，查询层的重写是一个默认的行为，一般情况下不会被关闭。我们会结合游戏内本身的一些概念、知识以及一些口语习惯对每个 Query 进行重写来实现更好的召回，一般不会重写为多条。

在整个系统中，我们同时支持了 Agentic RAG 和 Direct 两种模式。在任何一个模式下，我们都不接受使用检索层得到的资料进行回答。在检索层获得到具体的节点编号后，我们会查询事实层，并根据事实层的资料进行最终回复。

在 Direct 模式之下，每一个被召回的节点都会自动适当的扩大节点上下的 Window，默认值为 2（总计 5 条），实现所谓的 Small to Big。Agentic RAG 模式下则是 Agent 将会自己决策需要查询哪些节点以及使用多大的窗口。

考虑到系统涉及对不同查询层的聚合，我们默认采用 RRF 聚合；一般单个查询方式提供 30 个 Chunk 并聚合选中前 12 个 Chunk；PageIndex 不涉及聚合，他会直接提供最终找到的结果（PageIndex 默认行为）；我们没有设计 Reranker 模型，如果需要 Reranker 则通过单独的 LLM 请求实现；Agentic RAG 模式不涉及聚合与Reranker，它获取原始查询，然后自主决策行为并恢复，不过要受限于预设的 Budget 轮数。

### 自进化

事实上，我们的文档仓库的质量并不高。有很多问题可能更多的依赖于一些经验传授，而没有被记录到仓库中。也有一些仓库的内容是过时的，导致会返回一些错误的结果。

这就是自进化系统存在的意义，当用户发现自己的问题没有得到正确的回答，他可以向整个系统提出一个反馈。反馈本身只会去描述这个事情正确的样子应该是什么样子的，而不会明确要求你应该去哪里修改这个数据仓库，这不是用户的任务。

每一条反馈都会被系统记录，根据整个 log 系统去来定位他们应该去修改哪一个快，LLM 参与这个过程，来确认以前的哪些事实层的节点有错误，正确的形式应该是什么样子的。

当然，我们并不允许AI直接对整个系统进行修改。整个自进化系统都在人工的监督下运行，任何涉及事实层内容修改的地方，都会要求人工的介入与确认，并在修改后定时重新生成检索层。

过时是任何大规模企业数据库都不得不考虑的问题，而实际上，我们这个系统中并没有任何地方用来处理过时，脚本是没有办法判断这个问题的。

metadata 会在最后的回答层帮助我们解决这个问题，由于我们所有的信息都会回到最终的事实层，而事实层是可以记录文件的创建时间。如果相互冲突的数据被同时召回，那么系统会优先根据创建时间来决定更新的那个文档，或许更可能是真的，当然他需要在这个时候警告用户，我们出现了文档冲突的问题，需要人工决策。

### 总结

这就是这个 RAG Demo 所提供的全部内容，它基本定义了我去做 RAG 的基本操作逻辑，但其实没有做透很多工程上的优化，比如很多涉及分支技术方案以及一些参数的选择，它们更多的是基于一些经验，而没有经过细致的实验，确实变量太多了。


## 游戏知识图谱

这是一个单独的 RAG 项目，也来自网易的实习经历，不过侧重点有些不同，也有更多的参与者。

我们的最终目标是构建一个游戏内部的知识库，并且提供一个QA BOT来让策划或者是玩家进行使用。比如这个物品怎么获得，这个关卡该怎么通过等等等等内容。

和前面的项目一样，我们需要关注数据应该如何获取，以及最终应该如何查询并回答，以及不得不考虑的问题，这个系统应该如何被更新。

### 构建游戏知识图谱

在讨论数据库的时候，最关键的问题依旧是数据。如何获取游戏内部的数据、玩法是什么样的、有什么物品、描述又是什么样的。

其实我们最开始希望去使用策划的文档，但是这是一个非常失败的尝试，所有的策划文档都严重过时，且存在大量的自我冲突，难以进行对齐。

我们采用了从代码仓库中获取真实情况的方法，这对于游戏这种场景来说相对更加可靠。我们从 UI 工程文件入手，去看相关策划配表的加载，从代码仓库中提取各种不同类型的实体，然后通过本身的类属性，形成一个大致的分类。比如物品，制造配方，原料，地区，玩法，怪物等。

**注意，Agent 去全面阅读代码然后抽取是不现实的，游戏源码行数在千万级，现有的上下文窗口不可能接受，我们需要一种 Map and Reduce 的方法，也需要从代码中基于规则去发现，而不是基于 LLM 去发现；从数据文件出发，逻辑透传UI文件，因为不是所有 UI 文件都有用。**

这里的具体分类是AST， AI 和策划一起做的，最终的结果是构建了一个局部地区有二级分类，大部分地区只有大分类的架构。 我们得到了约 2w 节点，部分节点之间存在边的连接；有1万节点有边，总边数约为3万；边全部的单向的且不存在属性。单个节点大致的信息有节点本身的名字，在策划配表中的描述文字，分类 metadata 和连接边的相关信息。边本身是从程序中获取的，而不是源自于模型、确定性代码或人工的标注。

这些边依旧从代码中获取，边本身也可能是节点，但我们在系统中没有处理这个问题，且并不是所有的代码的边的关系都被建模了，类似关卡内的触发器我们就没有处理。这当然是一个相对妥协的图谱系统，不过我们确实需要控制最后的总变数数量，来保证查询图谱更加可用。

从以上结构能看出，他本质是一个类似 LLM Wiki 的图谱，但此时图谱为了降低成本和保持总结可信度是通过代码与程序关系建立的。我们也从使用 Markdown Wiki 改为使用 JSON Wiki，每个节点依旧保留一定的树状分类层级结构。这就是整个系统的事实层，一张自包含信息的图谱。

Agent 基于 SVN Commit 信息对这个新引入的数据进行更新，根据之前形成的架构文档更新新的分类和节点，同时交叉审核保证新的 SVN 提交不会导致过去的分类体系做修改。

对于哪些可能涉及不对玩家展示（非外放的信息），通过loghub 的命中进行识别，实际上是白名单机制，非白名单信息交给策划手工处理。

### 在图谱上查询

图谱这里就不再涉及什么增强结构了，我们只需要考虑如何在图谱上进行查询。

由于本身分类系统的能力有限，部分子类别可能会有上百或者大几百个实体，想要构建类似于 PageIndex 的结构化索引系统并不现实（其实尝试一下 Tree Search 也不是不行）。我们依旧需要使用类似于 LLM Wiki 的思路对整个系统进行一些冷启动。

我们提供了一个基本的 wiki-search工具，通过聚合 BM25 以及向量检索来冷启动找到节点。
```json
{"action":"tool","tool":"wiki.search","query":"检索词"}
```
这里不涉及过多的工程优化，其实基本的思路和我们前面都是一样的。

既然有了检索分块用的工具，但然也有一些阅读分块的工具。
```json
{"action":"tool","tool":"wiki.read_page","path":"wiki/example.md"}
```

当你找到了一些节点以后，你也可以去顺着节点的边去查询
```json
{"action":"tool","tool":"graph.search","path":"node"}
```

当然，模型需要有可以回答问题的时候
```json
{"action":"final","answer":"最终回答"}
```
回答的时候需要提供证据。

这个系统是完全 Agentic RAG 化的，我们并不讨论普通的 QA，这点其实和 LLM Wiki 的思路一样，解析动作、执行工具，把结果作为 observation 加入下一轮上下文；然后他可以继续重写查询，展开图查询或者在认为知识足够后回答问题。允许在图谱多跳，通过提示词进行了一定约束，并允许设置查询的 budget，默认可以设置为 6 跳。

最终的回答层，会给所有路线都预留份额，sqlite 两路 RRF 聚合的结果，单路 top-k 也可以返回。Graph 这里由 Agent 决定是哪些返回（Agentic 是这样的）。  在条件允许的情况下，都是一个llm 作为 reranker 。 

边实际上可以拥有属性，但在之前的系统里只被建模为了单向边，如果有属性可能会带来更好的收益，给 Agentic RAG 提供更加充足的决策信息。

改进版本思路基于树进行 requery，通过树上的 Agentic 检索提供补充信息用来 Requery，然后再使用传统的 BM25 和 dense vec 检索去获取节点，然后在图上扩展，收集信息，用于回答。

## AI-PM：尝试炼化产品经理

AI-PM 的初心是为了让我稍微拥有一点产品的思维，毕竟是 AI Coding 时代，也不能单纯研究技术，还是要稍微了解一下产品，看看能不能变成一个 Builder。

不过现在我的正式工作以及一些需要学习的内容，基本上已经让我精疲力尽了。我不可能真的成为一个专业的产品经理，那么我希望尝试一下炼化 Lenny Rachitsky，他为大家提供了一个订阅的数据库，包含了很多产品上的经验，这就是 AI-PM 想要做的。

### 事实层与检索层

进入知识库的内容文件是 349 篇 Newsletter 和 289 个 Podcast，共 638 篇。但是在交给 Docling 进行解析之前，我们需要一些基本的清洗和增强。

所有的数据都是 markdown 文档的形式，但标题层级并不明确，且包含了一个无法被解析的 YAML 字段。Newsletter 主要做确定性的标题归一化，把必要的内容交给标题。Podcast 则在 speaker turn 的边界插入章节和小节标题。章节标题来自模型，但正文顺序仍然保留。他们都是为了保持整个文档系统的结构，这点我们在整个 Blog 的开头就提到过了。

接下来，Docling 的 Markdown `SimplePipeline` 把增强后的文档转换为 `DoclingDocument`。项目关闭了远程和本地图片抓取，所以事实层只保存图片 URL、caption 和 Docling 引用。由于所有的图片其实都包含了 caption，因此这里的图片实际上并没有进行增强。

我们依旧使用了事实层和检索层的分离，使用 Hybridtrunker 将整个事实层进行切片。依旧使用 contextualize(chunk) 自动拼接标题结构到每个 Chunk 中，依旧做了 Summary 的增强。

### 查询层

事实层构建完成之后，项目才会单独生成检索索引。关键词索引使用 SQLite FTS5，把标题、章节、元数据和正文分开存储，并给它们不同的权重；语义索引使用 2048 维的 GLM-Embedding-3。两套数据库是独立的，构建结果通过统一回到事实层再回答问题。

Direct 模式下，问题会先经过一次面向语料库的 Query Rewrite。重写结果同时包含适合语义检索的自然语言查询，以及适合 FTS5 的关键词和短语。关键词和向量两路各取最多 60 个候选，再使用 RRF 合并，保留 12 个 locator。这里的 RRF 只是合并排名，不是在判断事实真假，只有事实层才会作为证据。

每个被选中的 Chunk 都会读取命中 DoclingDocument 对象本身及其两侧各两个相邻对象，并在同一文档内去重。如果存在无法检索，那么大概率是事实层出现了变动但是没有更新检索层，则需要考虑重建检索层。检索索引是派生物，只有事实层能够回答这段内容现在是否仍然是我们承认的那一段。

Agentic 模式的差异主要在于谁来决定下一次检索。它首先把关键词和语义两路各自的少量候选交给 Agent，不做 Direct 模式里的自动 RRF，也不做隐藏的 Query Rewrite。之后 Agent 可以重新选择关键词搜索、语义搜索、读取某个 locator 的窗口，或者对已经读取的证据的内容进行观察。

Agent 也不能因为自己看到了一个检索结果就直接相信它。只有 `read_source_window` 产生的 Evidence 才能进入回答上下文，读取次数、工具轮数和证据 token 数都受到 budget 限制，最终回答中的引用还会检查是否确实对应本轮已经读取的证据。

Agentic RAG 并没有绕过事实层，它只是把“搜什么、搜几次、读多大的窗口”从固定程序交给了 Agent。固定检索和 Agentic 检索使用不同的策略，但两者最后都必须通过同一个证据边界。

看起来这个项目里我们并没有做什么新东西，不过它有趣，而且有一点用。

这个项目中完全放弃了类似于 PageIndex 的结构化索引系统，因为我们没有那么明确的可信的索引结构。我也尝试了将所有的文档变成一个 LLM Wiki 的知识库，确实看起来做得像模像样，但是在回答质量上感觉不出来。这就是构建图，成本很高，但收益并不明确。
